# Cross-platform repository verification — 11/14/2026

**Repository:** `KingStephan18/research-portfolio`
**Public baseline:** `f533b993e69c2b9cd15ea728ea6fbcc933648820` (10/24/2026)
**Scope:** isolated local Windows clone, published source, authored synthetic tests and integrity verification. Changes are a proposed local candidate, not a published GitHub release.

## Reproduced failures before correction

- **Windows default checkout:** system Git `core.autocrlf=true` converted LF to CRLF in tracked text files. The SHA-256 manifest, generated from LF content, reported widespread hash mismatches even though `git status --porcelain` remained clean. Re-cloning with `core.autocrlf=false` restored a consistent baseline manifest (41 entries).
- **Windows Python output encoding:** with Windows 11 / Python 3.13.15 and a legacy `cp1252` output encoding, `test_unicode_scalar_claim_preserved` failed because the CLI could not print a non-ASCII claim. In a LF-preserving baseline clone all other tests and the manifest passed.
- Both failures were reproduced on 11/14/2026 before applying the candidate repairs. This is not evidence of a vulnerability in the public runtime or compromise of any account.

## Bounded repairs in the candidate

1. Added `.gitattributes` to preserve LF for manifest-covered text files on fresh checkouts across platforms; the screen PDF remains binary.
2. In `verify.py`, set `PYTHONUTF8=1` for test subprocesses. In `evidence-ledger/ledger.py`, set UTF-8 on CLI stdout when supported; JSON field content and committed sample outputs are unchanged.
3. Added a read-only GitHub Actions workflow that invokes `python verify.py` on push and pull request. The checkout/setup actions are pinned to full, first-party release commit SHAs. No credentials are persisted by checkout.
4. Updated README links and maintainer-facing evidence, retaining the existing synthetic-versus-real research, attribution, acting material and archive boundaries.
